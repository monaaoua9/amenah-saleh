# streamdb: design decisions

The reasoning behind the main choices. Data flow, cluster mode and known gaps in full: [ARCHITECTURE.md](ARCHITECTURE.md).

## Scope

A distributed stream-processing engine: gRPC ingestion, keyed event-time windows (tumbling, sliding, session), backpressure, aligned-barrier checkpoints, exactly-once results, and a cluster mode with automatic recovery.

## Decisions

**A producer is pinned to one lane by hashing its name.** Per-producer order holds and sequence-number dedup is a single map lookup. Lanes then route each event to a worker with `Hash` (keyed state stays on one worker) or `RoundRobin` (stateless stages only; it refuses to split keyed windows).

**Two layers of backpressure.** Every channel is bounded, and on top an event-count semaphore caps in-flight events across the whole pipeline, which is what really bounds memory. Credits come back only after the worker has handed output to the sink, so a slow sink slows ingestion. `Submit` blocks (the gRPC handler stops reading and HTTP/2 flow control stalls the client); `TrySubmit` / `-shed` returns `RESOURCE_EXHAUSTED` instead.

**Watermark = max(event time) − Disorder, and workers take the minimum across lanes.** A quiet lane can't push time past data still queued on a busy one. A window fires when the watermark passes its end, stays around for `Lateness` and re-fires (`Late: true`) for stragglers; anything older is counted and dropped, not silently lost.

**Aligned barriers (Chandy-Lamport in the form Flink uses).** The coordinator injects a numbered barrier into every lane; a task snapshots once it has seen the barrier from every upstream, holding back records from upstreams whose barrier already arrived. That makes channel state empty by construction, so nothing has to be recorded. The price is that alignment stalls the fast inputs while they wait for the slow one.

**A checkpoint exists only when `_COMPLETE` is written.** Snapshots are tmp + fsync + rename, and the last three are kept. The sink stages output per epoch and emits it only after that checkpoint is durable, so uncommitted output is discarded on crash and regenerated by replay.

**Exactly-once = restore + producer replay + sequence dedup.** Every `Ack` carries `committed_seq`, the highest sequence inside a completed checkpoint. The producer client keeps batches above it and resends after a broken stream; lanes drop `Seq <= last` per producer. `TestExactlyOnceAcrossCrash` checks the output equals a run with no crash. It requires a producer that follows the protocol; a hand-rolled client has to.

**Rescaling through 128 key groups.** A worker owns a range of groups. On restore each new worker loads every old snapshot and keeps the keys it now owns. It needs a keyed partitioner.

**Cluster nodes carry no durable state.** The master holds ingest, lanes, sink, coordinator and checkpoint store; workers run the same window code behind a different environment (a stream instead of in-process calls). A lost stream cancels the engine and the supervisor restarts it from the last checkpoint. Simple, but recovery is a full rollback: surviving workers are restored too.

## What's not exactly-once

A crash between emitting a sink epoch and writing its `_EMITTED` marker re-sends that one epoch, so it's at-least-once for that epoch and downstream dedups on (key, window start). After a rescale the watermark restarts at the slowest old worker's, so a very late event can be accepted that an unscaled run would have dropped.

## Known gaps

`Advance` scans all open windows once per batch (fine to ~100k open windows, then a timer heap is needed). The latency histogram is log-bucketed, so quantiles are accurate to about 25%. No source offsets are kept beyond the per-producer last sequence.
